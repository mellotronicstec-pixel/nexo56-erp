# 12 perguntas de modularidade — `core.service_orders`

| #   | Pergunta               | Resposta                                                                                                                                                                                                                                                                                        |
| --- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Classificação**      | `CORE`. Uma assistência técnica sem Ordem de Serviço não é uma assistência técnica — é um cadastro de aparelhos.                                                                                                                                                                                |
| 2   | **Pode desativar?**    | **Não.** `CORE` não é desativável pelo tenant nem pelo plano; há teste verificando que a tentativa é recusada.                                                                                                                                                                                  |
| 3   | **Dependências**       | `core.customers` e `core.equipment`, declaradas explicitamente. Mais o contexto de unidade, que é infraestrutura e não feature.                                                                                                                                                                 |
| 4   | **Dependentes**        | Orçamento (09), Peças (10), Financeiro (12), Garantia (13), Agenda (14), Central de Trabalho (15), Comunicação (16) e Portal (17) dependerão desta. O workflow (08) é o primeiro.                                                                                                               |
| 5   | **Dados ao desativar** | Não se aplica (não é desativável). Se um dia fosse: **a OS permanece**. É registro histórico operacional, e o mecanismo de dependências nunca apaga dado — ele impede ativação incoerente.                                                                                                      |
| 6   | **Frontend**           | `/ordens-de-servico`, `/ordens-de-servico/nova`, `/ordens-de-servico/[id]`, `/ordens-de-servico/[id]/editar`, mais os atalhos na ficha do equipamento e na lista de recebimentos. Cada ponto verifica Effective Access no servidor; o item de menu só aparece quando a feature está disponível. |
| 7   | **Backend/API**        | Server Actions do módulo sobre a camada de aplicação (`createServiceOrder`, `updateServiceOrder`, consultas). Não há API pública ainda — e a regra mora no serviço justamente para que a futura API e o Nexo56 Mobile a reusem sem reimplementar.                                               |
| 8   | **Automações**         | **Nenhuma.** Os eventos ficam no outbox à espera do Rule Engine.                                                                                                                                                                                                                                |
| 9   | **Permissões**         | `service_orders.view`, `service_orders.create`, `service_orders.update` — avaliadas **dentro da unidade ativa**.                                                                                                                                                                                |
| 10  | **Plano**              | Entitlement `core.service_orders` em todo plano, por ser CORE.                                                                                                                                                                                                                                  |
| 11  | **Reativação**         | Não se aplica. O dado estaria intacto de qualquer forma: nada é apagado.                                                                                                                                                                                                                        |
| 12  | **Histórico**          | **Sim, em duas camadas.** `service_order_timeline` guarda os fatos de negócio (append-only); `audit_logs` guarda a trilha de segurança, incluindo o texto anterior do relato quando ele é corrigido. A própria OS é histórica: não se exclui, e cliente, equipamento e unidade não mudam.       |

## Dependência formal

O grafo de `feature_dependencies` é o único mecanismo usado — não há verificação
de plano espalhada pelo módulo. Ele impede ativação incoerente e **não** destrói
dado. No banco, `ON DELETE RESTRICT` garante que cliente, equipamento, unidade e
recebimento com OS associada não desapareçam por acidente.
